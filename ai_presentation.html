deep-dive · LLM 코딩
코드 품질은 올라갔다
하지만 생산성은 다른 문제였다
좋아진 점
  • ✨
    코드 품질 향상

    패턴 제안, 엣지케이스 보완, 더 나은 네이밍 등 혼자 작성할 때보다 완성도가 높아졌다.

한계로 느낀 점
  • 🧩
    전체 설계가 반영되지 않음

    생성된 코드는 부분적으로는 동작하지만, 전체 아키텍처·설계 원칙과 맞지 않는 경우가 많았다.

  • 🐛
    디버깅·검토 시간이 추가로 발생

    생성 코드의 의도를 파악하고 수정하는 시간이 생각보다 길었다. 생산성 이득이 상쇄되는 경우도 있었다.

limitations
한계 및 주의사항
  • ⚠️
    100% 신뢰 불가

    출력 결과는 항상 검증 필요. 틀릴 수 있음을 전제로 활용해야 한다.

  • 🔐
    정책·보안은 반드시 내부 기준 확인

    AI 답변을 초안으로 삼되, 최종 판단은 내부 기준에 따를 것.

  • 🏢
    사내 특화 시스템은 부정확할 수 있음

    회사 고유 환경·레거시 시스템에 대한 AI의 이해는 제한적.

  • 🤖
    대량 생성 ≠ 사람에게 유효한 콘텐츠

    블로그 200개 경험처럼 — AI가 쓴 글은 AI만 읽는다. 맥락과 의도는 사람이 넣어야 한다.

conclusion · 전하고 싶은 것
AI는 판단을 대신하지 않는다
판단을 더 빠르게 내릴 수 있게 돕는다
실제로 효과적이었던 방식
  • 사람이 검토하는 루프가 있을 때
  • 판단 보조 · 초안 생성 · 구조 정리
  • 기존 업무 흐름에 붙이는 방식
기대와 달랐던 방식
  • 사람의 맥락 없는 완전 자동화
  • 전체 설계 없이 LLM에만 의존한 코딩
  • 검증 없이 바로 적용
